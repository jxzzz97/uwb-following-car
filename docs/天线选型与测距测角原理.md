# 天线选型与测距测角原理

## 1. 设计分工：随身端保持简单，车端承担方向测量

本项目采用的硬件方案是 **Tag 全向单天线，Anchor 三天线接收阵列**。Tag 佩戴在人身上，Anchor 随车移动；这里的 Anchor 表示协议中的车载测量节点，不表示必须固定在世界坐标中。

| 设计项 | Tag 随身端 | Anchor 车载端 |
| --- | --- | --- |
| 天线方案 | 全向单天线 | 三天线阵列，接收通道 RX0 / RX1 / RX2 |
| 主要任务 | 发起交互、参与双向测距、发送测角包 | 响应交互、采集多通道信号、计算来向 |
| 是否需要本端测方向 | 当前应用不需要 | 车辆需要知道目标偏左还是偏右 |
| 软件证据 | 收包使用 `EN_UWB_RX_0`，测角阶段重复发送信号 | 测角阶段使用 `EN_UWB_RX_ALL`，等待三路接收事件 |

接收端通过阵列比较同一入射信号的相位，发射端不必也安装测角阵列。该分工与 UWB AoA 的基本结构一致，参见 [FiRa 对 PDoA / AoA 的说明](https://www.firaconsortium.org/resource-hub/blog/uwb-terminology)。

## 2. Tag 为什么使用全向单天线

使用者行走和转身时，随身端相对车辆的朝向不断变化。选择全向天线是为了增加目标周围的覆盖范围，减少必须将 Tag 特定一面始终对准车辆的要求。单天线则满足本项目的收发与测距职责，避免在随身端增加没有被当前控制链使用的阵列几何和通道相位标定。

这是基于应用职责的取舍，不是“天线越少，测距必然越好”。实际体积、成本和功耗取决于具体板卡、天线和收发时序，本文不以天线数量直接推算续航。

“全向”通常指设计平面内较广的方向覆盖，不表示整个三维空间处处等增益。人体遮挡、佩戴位置、天线极化、金属附件和姿态仍可能导致弱信号或角度波动。安装时应保留天线周围空间，并记录佩戴方式。

Tag 工程中保留了 SDK 的 `EN_ANTENNA_0_0_3D` 和 `TRIANGLE_UP` 配置名称。**这些名称不能单独证明实物装有三根天线**：当前 Tag 应用没有执行三通道 PDoA 接收或本地 AoA 解算。实际硬件选择按单天线 Tag 接口与板卡设计确认，SDK 共用的阵列配置不能与随身端实物形态混为一谈。

## 3. Anchor 为什么采用三天线

单次距离测量只能说明“目标离我多远”。在车辆周围，左前、正前和右前的多个位置可能拥有相同距离，因此控制转向还需要方向信息。

接收阵列提供已知的空间基线。同一波前传播到不同天线时，其路径和相位不同，可以据此估计来向。三路接收可形成三对相位差：

```text
PD01：RX0 与 RX1
PD02：RX0 与 RX2
PD12：RX1 与 RX2
```

三天线提供了多基线观测及二维角度扩展的硬件基础；并不意味着三对相位完全独立，或任意固件都会同时融合三对结果。在一致的差分定义下，三对相位之间存在代数关系，噪声、通道偏置和多径会破坏理想关系。

对于本版单个水平角，一对适当布置的接收天线就能提供基本相位基线。采用三天线参考硬件的工程价值，是同时保留 RX0 的测距/通信通道、三路测角采集、多对相位诊断与后续三维算法扩展；不能写成“PDoA 测一个方向必须恰好三根天线”。当前也没有实现利用 PD01/PD02 自动修正 PD12 的融合逻辑。

**当前版本的实际取舍是：三路采集、三对 PDoA 保留诊断，控制用水平角只取 PD12。** 原 App 将 RX1–RX2 定义为水平基线，使用其简化反三角解算，俯仰输出置零。这样将控制所用方向约束到所选基线，避免直接套用完整三维 LUT 输出；它不是三对融合算法，也不消除真实俯仰对单基线观测的影响。

SDK 中存在 `cb_framework_uwb_pdoa_calculate_aoa()`，其内部调用偏置补偿和三维 LUT。当前 Anchor App 没有调用这条完整 AoA 路径，因此不能把“三天线硬件”“SDK 三维能力”和“本版已实现三维定位”写成同一件事。

## 4. 距离与方向是两条不同的测量链

| 测量量 | 方法 | 主要依据 | 当前计算位置 |
| --- | --- | --- | --- |
| 距离 DIST | DS-TWR 双边双向测距 | 双端收发时间戳 | Tag 汇总双端时序并计算，再回传 Anchor |
| 到达角 A | PDoA → 等效水平来向 | Anchor 多天线接收相位与基线 | Anchor |

距离不由 RSSI 强度直接换算，角度也不是由左右两个测距值相减得到。RSSI 在本版保留为接收信号诊断量。

### 4.1 DS-TWR 为什么需要多次收发

基本交互为 `Poll → Response → Final`。双方记录本地发送和接收时刻，分离无线传播时间与设备回复等待时间。常见的双边测距表达为：

```text
Tprop = (Ra × Rb - Da × Db) / (Ra + Rb + Da + Db)

Ra：Tag 从发 Poll 到收 Response 的本地时间间隔
Da：Tag 从收 Response 到发 Final 的本地回复间隔
Db：Anchor 从收 Poll 到发 Response 的本地回复间隔
Rb：Anchor 从发 Response 到收 Final 的本地时间间隔
距离的物理基础：r = c × Tprop
```

双边时序用于降低相对时钟偏差带来的影响，不要求把两端本地时钟直接当成同一个时钟。它仍受时间戳、硬件延迟和传播环境影响。通用原理可对照 [Rohde & Schwarz 白皮书第 6 章](https://www.firaconsortium.org/sites/default/files/2024-01/rohde-schwarz-uwb-white-paper-jan-2024.pdf)。

本工程的传播时间计算进入厂商预编译库。可见 SDK 的距离包装实际使用：

```c
distance = DS_TWR_T_Prop * 30 - 18617 + initiator_bias + responder_bias;
```

这是当前 SDK 的换算与固定补偿表达式，应用层以 cm 使用结果。`30`、`18617` 属于当前 SDK 链路，不能把未经确认的底层时间单位直接代入物理公式，或把固定补偿项当成车辆安装偏移。更换 SDK、信道或射频硬件后，应重新核对厂商定义与实测标定。

## 5. PDoA 如何转为 AoA

在远场平面波、基线已知和通道已标定的近似下，设天线基线长度为 d，θ 从阵列正前方零度量起：

```text
路径差 Δl = d × sin(θ)
相位差 Δφ_rad = 2π × Δl / λ
θ = asin(Δφ_rad × λ / (2πd))

若相位差使用度：
θ_deg = asin((Δφ_deg / 360) × λ / d) × 180/π
```

测得的是接收相位差，AoA 是根据阵列几何反推的方向。不同资料可能从基线方向定义角度而使用 `acos`；必须先比较零度基准和相位差符号，不能直接交换公式。原理图和角度定义参见 [Rohde & Schwarz 白皮书第 7 章](https://www.firaconsortium.org/sites/default/files/2024-01/rohde-schwarz-uwb-white-paper-jan-2024.pdf)。

### 5.1 当前代码中的实际计算步骤

Anchor 的 `EN_APP_STATE_PDOA_POSTINGPROCESSING` 使用：

1. 从 5 包统计结果中取 `median.rx1_rx2`。
2. 减去 `s_pd12Bias`，参考值为 **77.09°**。
3. 将补偿后的相位折回 `[-180°, 180°)`。
4. 按 `Δl = PD12_comp / 360 × 3.753 cm` 计算路径差。
5. 使用 `d = 1.88 cm` 计算 `sinVal = Δl / d`。
6. 将 `sinVal` 限制到 `[-1, 1]`，执行 `asin` 并转换为角度。
7. 经过大跳变保持策略后写入 `s_aziResult`，同时将 `s_eleResult` 置零。

`3.753 cm` 是当前 Ch9 解算所用波长近似，`1.88 cm` 是该 App 使用的基线参数，约为半波长。这两个量与射频阵列有关，不是车宽或轮距；更换底盘尺寸无需修改它们，更换天线或射频信道则需要重新核对。

理想情况下近半波长基线在视场和相位歧义之间作折中，但不能据此保证没有前后歧义、多径或通道失配。`asin` 在侧向接近 ±90° 时对误差更敏感，本版车体目标处理另设置默认 ±80° 工作区；该软件阈值不等同于射频有效视场的实测保证。

### 5.2 为什么减去偏置，为什么进行相位折返

射频走线、接收链和天线相位中心会引入固定或随方向变化的误差。`s_pd12Bias` 用于补偿当前参考链路的相位零点，不是“向左打多少方向”的控制参数。换板、换天线或改变射频路径后，不能默认继续使用同一个偏置。

相位是周期量。例如 179° 与 -179° 只相差 2°，直接按普通数值处理会误认为跨越 358°。当前代码在偏置补偿之后执行相位折返；但前面的 5 包统计使用普通数值排序中值，并没有额外实现圆周中值，跨越 ±180° 的数据仍需重点检查。

更换射频硬件后的零点检查，应固定 Anchor 姿态，在远离近场影响与明显反射物的条件下，将 Tag 放在已知正前方向，记录多个距离和多帧 PD12。先确认偏置在这些条件下是否稳定，再按相位的周期性质估计零点；不能拿一帧就得出通用标定。随后还要检查左右已知角度的响应。若误差随方向明显变化，单一常数偏置不足，需要评估阵列几何、互耦、相位中心或完整标定模型。

### 5.3 为什么限幅，以及它的边界

测量误差可能使 `Δl/d` 超过数学定义域，直接调用 `asin` 会产生无效数。限幅保护计算域，但不会修复测量：超界后可能得到贴近 ±90° 的饱和值，不能把它解释为已确认目标恰好位于侧方。

例如手工构造的 `PD12_raw=167.09°`，扣除 77.09° 后为 90°，代入当前参数得到约 29.94°。这是公式示例，不是标定数据或角度精度证明。

## 6. 三维空间中的限制

对具有俯仰角 ε、水平角 α 的一般方向，理想水平基线约束的是：

```text
Δl / d = cos(ε) × sin(α)
单基线反解得到 asin(cos(ε) × sin(α))
```

所以高度差大时，单基线输出不能无条件视为真实水平角。将俯仰结果设为零只是应用选择，并未证明 ε 为零。

同样，DS-TWR 距离是空间传播距离；代码的 `X=DIST×sin(A)`、`Y=DIST×cos(A)` 是本版平面控制使用的等效坐标。当前没有根据 Tag 与 Anchor 高度差恢复真实地面投影距离，不能将输出当成已经完成三维矫正的地面坐标。
